# Player‑Cluster Scoring Overview

## What the script does
The **`run_score`** helper (exposed in `scripts/recommender/score_cluster_players.py`) evaluates a match by measuring how well the selected players from each national team align with **user‑chosen favourite clusters** for every macro‑position (Goalkeeper, Centerbacks, Fullbacks, Midfielder, Striker, Wingers).

---
### Data sources
1. **`convocados.db`** – SQLite database that stores the list of *convocados* (selected national‑team players).  The columns of interest are:
   - `pais` – country name (in Spanish).
   - `jugador` – player name (often a short version, e.g., `Kylian Mbappé`).
2. **Clustering JSON files** – generated by `assign_players_to_centroids.py` and stored under `data/clustering_maps/`.  Each file (e.g., `kmeans_striker_full_distances.json`) contains a list of clusters:
   ```json
   [
     {
       "cluster_id": 1,
       "players": [
         {"long_name": "Kylian Mbappé Lottin", "distance": 0.061183},
         ...
       ]
     },
     ...
   ]
   ```
   The `distance` is the Euclidean distance from the player vector to the *centroid* of that cluster.

---
### Matching players to clusters
1. **Name normalisation** – Both the DB names and the JSON names are passed through the same routine (`normalize_string` from `data/player_similarity/player_similarity.py`).  This removes accents, lower‑cases the string and collapses whitespace, ensuring that:
   - `"Kylian Mbappé Lottin"` → `"kylian mbappe"`
   - `"Kylian Mbappé"` → `"kylian mbappe"`
2. **Lookup dictionary** – For the *favourite* cluster of a position we build a dictionary that maps:
   - the exact name, the **full‑normalised** name, and a **short‑normalised** name (first two words) to the distance value.
   - This allows the short DB entry (`Kylian Mbappé`) to resolve to the distance stored for the longer JSON entry (`Kylian Mbappé Lottin`).
3. When iterating over the players fetched from `convocados.db`, we normalise the DB name and look it up in the dictionary.  If the name is not present we treat the contribution as `0`.

---
### Scoring formula
For each player that matches the favourite cluster we compute a **contribution**:
```python
contribution = 1.0 / distance   # distance > 0
```
The contribution is added to:
- `total_score` – the sum across **all positions and both teams**.
- `breakdown[position]` – a list of dictionaries containing:
  ```json
  {"player": "Kylian Mbappé", "country": "Francia", "contribution": 16.3444}
  ```
If a player has a distance of `0` (exact centroid) we treat the contribution as `0` to avoid division‑by‑zero.

---
### Execution flow (high‑level pseudocode)
```
run_score(match, favourite_clusters, db_path)
│
├─ Parse the match → (country1, country2)
├─ Load players for each country from convocados.db
├─ For each macro‑position:
│   ├─ Load the appropriate JSON file (cached after first read)
│   ├─ Build a lookup dict for the favourite cluster (exact + normalised keys)
│   ├─ For each player of both teams:
│   │   ├─ Normalise the name
│   │   ├─ distance = lookup.get(name) or lookup.get(normalised_name)
│   │   ├─ contribution = 1 / distance (or 0 if missing)
│   │   └─ Accumulate into total_score and breakdown
└─ Return (total_score, breakdown)
```

### Customising the score
- **Change favourite clusters** – edit the `favourite_clusters` dict in `t.py` (cluster IDs correspond to those in the JSON files).
- **Add new positions** – extend `POSITIONS` and provide a matching JSON file in `data/clustering_maps/`.
- **Different contribution function** – replace `1 / distance` in `process_players` with any other monotonic function (e.g., exponential decay) to penalise larger distances more heavily.
